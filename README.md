# 信息学奥赛自动出题流水线

用四个大模型（下称"四个槽位"）加一套机器裁判，把一道竞赛题从零做到可判题的数据包：
题面、标程、数据、错解、部分分、题解，全部自动生成，每一步都有机器验证。

**定位**：校内训练 / 自用，不是替代命题人，是把"出题这件事里机械的部分"自动化。

---

## 现在能做什么

已经完整跑通并成功打包的题：

| 题目 | 考点 | 耗时 | 关键指标 |
| :-- | :-- | --: | :-- |
| 最小最大负载 | 二分答案 + 状压 DP | 655s | 10 测试点，暴力 100 分被拦 |
| 树上三色装饰 | 树形 DP（三状态） | 1048s | 10 测试点，最大 3.9MB |

一次完整运行会产出：

```
problems/<题号>/
├── spec.py          # 子任务 / 测试点 / 约束（唯一真相来源）
├── statement.md     # 题面（含占位符，打包时由 spec 渲染）
├── sample/          # 样例输入输出
├── sol.cpp          # 标程
├── brute.cpp        # 1 号写的暴力
├── brute2.cpp       # 2 号独立写的暴力（互验用）
├── ref.cpp          # 4 号的独立实现（对拍用）
├── approach.md      # 算法思路（3 号审的就是这个）
├── impl_plan.md     # 4 号 的实现方案
├── wrong/           # 错解（必须掉分）
├── partial/         # 部分分程序 + 实测分值
├── editorial.md     # 题解
└── build/           # 数据包 zip + 各阶段检查报告
```

## 快速开始

**环境**：Windows + Python 3.12 + g++（w64devkit 放 `C:\w64devkit`，或任何在 PATH 里的 g++）

```bash
cd E:\oj工作区\oj
cp web/config.example.json web/config.json   # 然后填四个槽位的 base_url / api_key / model
python web/server.py --port 8771
```

浏览器打开 <http://127.0.0.1:8771>，填考点和难度，点「开始出题」。

**命令行也能用**：

```bash
python oj.py new my-problem        # 建题目录
python oj.py check my-problem      # 契约检查
python oj.py gen my-problem        # 生成数据
python oj.py solve my-problem      # 对拍
python oj.py attack my-problem     # 错解攻击
python oj.py calib my-problem      # 部分分定标
python oj.py build my-problem      # 打包
```

**没有 API key 也能跑**：把槽位的 `base_url` 填 `mock`，会用 `web/mock/` 里的素材回放
一道 `demo-pair`，用来验证整条流水线本身是否正常。

## 四个槽位的分工

| 槽 | 角色 | 产出 | 失败后果 |
| :-: | :-- | :-- | :-- |
| 1 号 | **作者** | spec、题面、样例、暴力、生成器、标程、思路、题解 | 重试 3 轮，仍不过 → 整题作废 |
| 2 号 | **审题者 / 第二份暴力** | 题面歧义审查；一份独立的暴力 | 审题崩了 → 跳过；暴力错了 → 只重做它 |
| 3 号 | **审查者** | 审思路、审代码，必须给出**能跑的反例** | 崩了 → 跳过审查，继续 |
| 4 号 | **实现者** | 先出思路再写独立实现；写错解和部分分 | 重试 3 轮，仍不过 → 整题作废 |

**设计原则：只有"产出内容"的槽会卡住流程，"检查"的槽失败只记警告。**
检查环节的价值是概率性地发现问题，不值得为它牺牲整道题。

## 流水线

```
S1   1 号 写 spec + 题面 + 样例
     闸门：oj check --spec + 三个渲染占位符 + 查重
     ↓ 缺占位符 → 只补题面（不动 spec）
     ↓ 撞题 → 带着"和哪道撞了"退回重写
S2   2 号 审题面（看渲染后的版本，不是模板）
     闸门：冲突列表为空
     ↓ 有歧义 → 带着冲突描述退回 S1
S3   1 号 写暴力 + 数据生成器
S3b  2 号 独立写一份暴力
     闸门：两份暴力在 200 组小数据上必须完全一致
     ↓ 不一致 → 3 号仲裁（题面 + 两份代码 + 冲突输入 + 两个答案）
        ├─ 判"1号错" → 只让 1 号 重写暴力
        ├─ 判"2号错" → 只让 2 号 重写暴力
        └─ 判"题面不清" → 才回退重写题面
S4   1 号 写正解 + approach.md
     闸门：编译 + 样例复算 + oj gen + 标程 vs 暴力 200 组 + 标程 vs 2 号暴力
S4b  3 号 审思路 + 审代码
     闸门：反例必须被机器验证（跑 sol vs brute，输出不一致才算真问题）
     ↓ 反例站住 → 退回 S4
S5   4 号 先出思路 → 再写 ref.cpp
     闸门：oj solve（300 组小数据 + 60 组中数据）
     ↓ 失败分流：小数据不一致 / Python 异常 → 退给 1 号；其余 → 退给 4 号
S6   4 号 写错解 + 部分分
     闸门：先甄别"假错解" → 再 attack + calib
S7   1 号 写题解
S8   机器 组装打包 → oj build
```

### `oj gen` 里干的三件事

生成数据时顺带做完三项体检，任何一项不过都当场退回，不等后面才发现：

1. **逐点校验**：每个测试点必须通过 `spec.check()` 的约束
2. **小数据对拍**：标程和暴力 200 组必须一致
3. **约束饱和度**：暴力不能通过全部测试点（否则说明数据没造满）
4. **复杂度体检**：标程在自己生成的数据上不能超 100% 时限

## 判定标准

分界线是：**能不能证明"这道题本身是错的"**。

### 会拦下来（硬失败）

| 检查 | 失败意味着 |
| :-- | :-- |
| 契约不完整 | 打不出包 |
| 样例复算失败（且暴力判定标程错） | 标程算错了 |
| 两份暴力不一致（仲裁后） | 题意有分歧 |
| 标程 vs 暴力不一致 | 标程算错了 |
| 标程 vs 4 号实现不一致 | 大数据上标程错了（小数据测不出） |
| 数据违反 `check()` | 数据非法 |
| 暴力通过全部测试点 | 数据规模没造满，这题谁写暴力谁满分 |
| 标程超 100% 时限 | 这题没法测 |
| 错解拿满分 | 数据分不出对错 |
| 部分分拿 100 或 0 | 它不参与区分 |
| 撞题（考点重合 ≥75%） | 和已有题目是同一类 |

### 只记警告

- 错解得分 1~99（掉分了，只是掉得不够多）
- 部分分得分偏离预期（**自动按实测改写 `expected.json`**）
- 标程用了 35%~100% 时限（余量偏小）
- 3 号审查不通过 / 无响应
- 题解缺章节、没提到某个分数

## 批量出题

界面上的「出题数量」填大于 1，会**串行连着出**，每道自动换一个子方向：

```
第 1 道：换根DP（二次扫描）
第 2 道：树上背包 / 树形依赖背包
第 3 道：树的最小支配集
第 4 道：树的最大独立集
第 5 道：树的直径 / 中心
```

子方向用完（或该考点没有菜单）之后，交给模型自选，靠查重兜底。

- 一道失败**不会中断**整批，只记录
- 同一时间只允许一个批量任务
- 数量上限 20

接口：

```
POST /api/batch   {topic, difficulty, count}
GET  /api/batch/<batch_id>
```

### 支持子方向菜单的考点

树形DP(8) · 状压DP(5) · 二分答案(5) · 贪心(4) · 最短路(5) · 线段树(5)

## 查重

出题前会把**最近的题库**塞进提示词（"不要出成同类型"），出完之后再机器比对一次。

- 标签先归一化：`状态压缩DP / 状压DP / 状压动态规划` → `状压DP`；难度标签全部丢弃
- 判据：考点集合的 Jaccard 相似度 ≥ 75%
- **只统计"成功出完并打包"的题**——失败的尝试不算数

题库来源两处：`problems/` 下还在的题 + `web/runs/` 里成功运行的 `spec.py` 原文
（目录被删也能追溯）。

## 已知限制

**没有查重之前，模型会疯狂重复。** 42 次历史生成里，30 次是"二分答案 + 状压DP"。
现在有了查重和子方向菜单，但题库越小防得越弱。

**暴力是"真值"，但两个模型可能同方向误解。** 两份暴力一致不代表对——它们可能都理解错了。
3 号仲裁能缓解，但不是根治。

**题面歧义无法根除。** 2 号是模型判断，有误报（代价是一次重写）也有漏报。

**难度完全没标定。** 你填"CSP-S T2"，出出来的可能是 T1 也可能是省选，没有环节检查。

**重试是"整体重写"。** 1 号 修 bug 时重写整个文件，容易修好一个弄坏另一个。

**流式会偶发中断（约 3%）。** 服务端吐到一半停住，自动回退非流式重发，结果不丢，
但那段时间界面没有输出。

## 排错手册

| 日志 | 含义 | 该做什么 |
| :-- | :-- | :-- |
| `两份暴力对不上` + 3 号仲裁 | 谁写错了 | 看仲裁结论，会自动退回对应的人 |
| `约束饱和度 OK：暴力在 N 个点上过不了` | 数据规模合格 | 正常 |
| `暴力通过了全部测试点` | 数据没造满 | 让它补大数据，或把子任务上限写实 |
| `标程在这个测试点上 RE` | 程序崩了 | 看 stderr；多半是递归爆栈或越界 |
| `标程就用了 40% 时限` | 余量偏小 | 这只是警告，不影响出厂 |
| `这些「错解」和标程一致，已移出` | 假错解 | 正常，说明 4 号 写的"错解"其实是对的 |
| `已按实测把 expected.json 改成` | 模型估错了分值 | 正常，以实测为准 |
| `流式失败…改用非流式` | 服务端断流 | 不用管，会自动重发 |
| `撞题了：和已有的「X」重合度 100%` | 题型重复 | **换个考点** |
| `服务重启，这次运行被中断` | 服务被重启过 | 重跑 |

## 更新日志

### 2026-11-11

**流程重构**

- 顺序改成：先出两份暴力互验（钉死"真值"），再出正解
- 3 号 从"写实现"改成"审查者"：读代码比写代码容易得多，而且给的反例能机器验证
- 4 号的实现拆成两步：先出思路，再写代码——失败更快

**归责修正**（以前经常让错误的槽重试 3 轮）

- 两份暴力不一致 → 3 号仲裁，分头退回
- 小数据对拍不一致 → 退给 1 号（那是 sol 和 brute 打架，和 4 号无关）
- 对拍时 Python 异常 → 退给 1 号（gen.py 炸了）
- 题面缺占位符 → 只补题面，不动 spec

**判定尺度**

- 错解攻击：从"必须 0 分"改成"至少掉 1 分"
- 部分分定标：从"必须等于模型估的分"改成"以实测为准，自动改写 expected"
- 复杂度：只有超 100% 才拦，35%~100% 只警告
- 审查者崩了：从"整题作废"改成"跳过审查继续"
- 题解分数对不上：从"失败"改成"警告"

**新增检查**

- 约束饱和度：暴力必须至少掉一个测试点
- 查重：考点 Jaccard ≥75% 打回
- 子方向菜单：同一考点自动错开考法
- 假错解甄别：和标程一致的"错解"移出攻击列表
- 批量出题

**环境与稳定性**

- 编译加 `-Wl,--stack,67108864`：真实 OJ 的栈是 8MB 起，本地默认 2MB 会误判递归爆栈
- 修 `subprocess` 超时后杀不掉子进程导致整条流水线卡死（超时 → 限时二次击杀 → 放弃等待）
- JSON 解析容忍 LaTeX 裸反斜杠（`\le` 之类会让 `json.loads` 直接失败）
- 中数据对拍改用最大子任务的约束上下文（以前拿到 n_max=20 却想生成 n=500，直接崩）
- 补数据时先清空旧的错解/部分分文件（残留文件会被当成新程序参与评分）
- 漏占位符只补题面，不重写 spec（以前会连测试点数都变）
